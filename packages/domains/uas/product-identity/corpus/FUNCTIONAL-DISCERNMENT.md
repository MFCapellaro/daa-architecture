# Functional Discernment

## Purpose

Functional Discernment determines the function represented by normalized observations.

It is the layer through which the First Corpus moves from describing products to understanding what those products do.

Functional Discernment does not begin with predefined product classes.

It allows functional structure to emerge from recurring observations across products, families, platforms, and manufacturers.

---

## Methodological Position

The Corpus follows this precedence:

```text
Data Origin
    ↓
Observation
    ↓
Semantic Normalization
    ↓
Functional Discernment
    ↓
Function
    ↓
Product Capability
    ↓
Product Class
    ↓
Characteristic Schema
    ↓
Comparison
```

Each stage depends on the evidence established by the preceding stage.

No later classification should be used to retroactively determine an earlier observation.

---

## From Term to Function

A raw product term is not necessarily a function.

The Corpus distinguishes:

```text
Raw Term
    ↓
Normalized Concept
    ↓
Functional Meaning
```

For example:

```text
"Spraying"
"Spray System"
"Spraying System"
"Liquid Application"
        ↓
Normalized Concept
        ↓
Liquid Application
        ↓
Agricultural Treatment
```

The exact normalization remains subject to evidence.

Normalization must preserve the original terminology and its source.

---

## Function

A **Function** describes what a system, subsystem, or component does within an operational context.

Function is therefore contextual.

A function is not defined solely by the name of a component.

For example:

```text
Tank Capacity
```

is a characteristic.

It may participate in:

```text
Liquid Storage
        ↓
Liquid Application
```

The characteristic does not itself constitute the function.

---

## Function and Product Capability

Function and Product capability are related but distinct.

```text
Function
    ↓
What the system performs

Product Capability
    ↓
What the system is able to provide
```

A function describes an operational role.

A Product capability describes an available ability emerging from one or more functions and their supporting characteristics.

For example:

```text
Spraying Function
        ↓
Liquid Application Capability
```

The Product capability may depend on:

```text
Tank Capacity
Flow Rate
Pump System
Nozzle System
Control System
```

No individual characteristic should be mistaken for the resulting capability.

---

## Function and Characteristic

A characteristic is an observable or measurable property.

A function is an operational role.

Therefore:

```text
Characteristic
      ≠
Function
```

A characteristic may support one or more functions.

A function may depend on multiple characteristics.

Example:

```text
                 Liquid Application
                         ↑
          ┌──────────────┼──────────────┐
          │              │              │
     Tank Capacity    Flow Rate    Nozzle System
```

This relationship is many-to-many in principle.

The Corpus must preserve this distinction.

---

## Functional Context

A function must retain its operational context.

The same physical capability may have different functional meanings according to context.

For example:

```text
Liquid Handling
      ↓
 ┌────┴────┐
 ↓         ↓
Storage   Application
```

Likewise:

```text
Movement
   ↓
 ┌─┴───────────────┐
 ↓                 ↓
Transport        Positioning
```

Context determines functional interpretation.

---

## Platform Independence

A function may exist across different physical platforms.

Example:

```text
Agricultural Treatment
        │
   ┌────┴────┐
   ↓         ↓
 Aerial     Ground
   │         │
 DJI/XAG/   XAG R
TopXGun
```

The platform changes.

The agricultural function may remain.

Therefore:

```text
Same Function
      ≠
Same Implementation
```

Platform should not be used as the sole basis for functional classification.

---

## Functional Convergence

Functional convergence occurs when different products perform substantially the same operational function.

Current Corpus signals include:

```text
DJI AGRAS
XAG P Series
TopXGun FP Series
        ↓
Agricultural Liquid Application
```

and:

```text
DJI AGRAS
XAG P Series
TopXGun FP Series
        ↓
Agricultural Material Spreading
```

These are preliminary functional convergence signals.

They do not establish identical implementation.

---

## Functional Divergence

Functional divergence occurs when products that appear similar perform different operational roles.

For example:

```text
Obstacle Detection
        ↓
Detection Function
```

is not necessarily equivalent to:

```text
Obstacle Avoidance
        ↓
Avoidance Function
```

Detection may provide information.

Avoidance may use that information to alter movement.

Therefore:

```text
Detection
    ≠
Avoidance
```

even when both belong to the same operational system.

---

## Function Composition

Complex capabilities may emerge from multiple functions.

Example:

```text
Obstacle Detection
        ↓
Obstacle Interpretation
        ↓
Path Adjustment
        ↓
Obstacle Avoidance
```

Likewise:

```text
Position Detection
        ↓
Navigation
        ↓
Path Planning
        ↓
Autonomous Operation
```

Functional discernment therefore examines relationships between functions rather than treating every observed feature as an isolated category.

---

## Function Emergence

A Product capability may emerge from the interaction of multiple functions.

For example:

```text
Navigation
     +
Obstacle Detection
     +
Path Planning
     +
Control
     ↓
Autonomous Operation
```

The resulting Product capability is not reducible to any single characteristic.

This distinction is essential for later comparison.

---

## Functional Granularity

Functions may exist at different levels of abstraction.

Example:

```text
Agricultural Treatment
        ↓
Liquid Application
        ↓
Spraying
        ↓
Nozzle Operation
```

The Corpus must not collapse these levels prematurely.

Each level may represent a different conceptual role.

Functional granularity should emerge from recurring relationships and evidence.

---

## Functional Evidence

Functional interpretation requires evidence from:

1. original terminology,
2. operational context,
3. recurring observations,
4. relationships between characteristics,
5. cross-product recurrence,
6. cross-platform recurrence,
7. manufacturer terminology,
8. independent corroboration where available.

The strength of a functional interpretation depends on the quality and recurrence of its evidence.

---

## Evidence States

Functional interpretations progress through evidential states:

```text
Observed
    ↓
Normalized
    ↓
Function Candidate
    ↓
Functionally Corroborated
    ↓
Discerned Function
    ↓
Product Capability Candidate
    ↓
Established Product Capability
```

These states must remain distinct.

A function candidate is not an established function.

An established function is not automatically a Product capability.

---

## Manufacturer Identity

Functional normalization must not erase manufacturer identity.

Different manufacturers may describe equivalent functions differently.

Therefore:

```text
Manufacturer Language
        ↓
Normalized Function
```

The original manufacturer language remains attached to the normalized concept.

This preserves both:

```text
Shared Meaning
```

and:

```text
Manufacturer Difference
```

This distinction will later allow the Corpus to identify potential **manufacturer DNA** without confusing terminology with function.

---

## Functional Discernment and Product Class

Product Class is downstream from functional discernment.

The Corpus should not begin with:

```text
Drone
Sprayer
Spreader
Rover
```

as definitive classes.

Instead:

```text
Observed Functions
       ↓
Functional Structure
       ↓
Recurring Product Capability Pattern
       ↓
Product Class Candidate
       ↓
Discernment
       ↓
Product Class
```

A Product Class should emerge from a stable functional pattern.

---

## Functional Discernment and Comparison

Comparison is downstream from functional normalization.

The Corpus must not compare raw terms as though they were equivalent.

Instead:

```text
Raw Observations
       ↓
Normalization
       ↓
Functional Discernment
       ↓
Comparable Concepts
       ↓
Comparison
```

This allows comparison to distinguish:

```text
Same Function
Different Implementation
```

from:

```text
Different Function
Similar Terminology
```

## Unresolved Questions

The Corpus intentionally leaves the following questions open:

* What constitutes the minimum identity of a function?
* At what level should functions be normalized?
* Which functions belong to the product and which belong to its subsystems?
* When does a function become a Product capability?
* Which capabilities define a Product Class?
* Which characteristics are function-defining?
* Which characteristics are merely descriptive?
* How should manufacturer-specific functions map to shared functional concepts?
* How much functional convergence is required for comparison?

These questions must be resolved through evidence rather than assumption.

---

## Discernment Rule

Functional Discernment separates:

```text
What is observed
       from
What it means
```

and:

```text
What it means
       from
What it does
```

and:

```text
What it does
       from
What it is capable of
```

and finally:

```text
What it is capable of
       from
What class it belongs to
```

---

## Core Principle

> **Function is discerned from coherent relationships between observations and operational context.**

A function is not assigned merely because a term appears similar.

It emerges when observations, context, recurrence, and relationships provide sufficient evidence for a stable operational meaning.

---

## Integrity

Functional interpretation must remain traceable to normalized observations and their original sources.

No function should be established solely through analogy, naming convention, product category, or assumed equivalence.

Uncertainty must remain explicit until sufficient evidence allows discernment.

The Corpus preserves the path from source to function.

```text
Source
  ↓
Observation
  ↓
Normalization
  ↓
Functional Discernment
  ↓
Function
  ↓
Product Capability
```
